## 3. 分流去向：这些问法**不归本 skill**

| 问法 | 归哪 | 依据 |
|---|---|---|
| 「现场这台库上有哪些规则、现在什么状态」 | Skill / API 现查（现场实例事实不在本体） | capability §3 问法表；N7 |
| 「延迟 500ms 算不算高」「阈值是多少」 | 监控 / Skill 阈值表 | N5；02 号 §0 分工 |
| 「这次故障的根因是什么」 | 两半分开：候选机制 ＋ 证据缺口走 diagnose_mechanism；**根因定论走人** | N1；capability §3 |
| 「这两条约束互斥吗」 | 只有 3 条编译期形状检查（D1 约束 ID 引用的状态不在状态机 / D3 关系类型缺声明 / D4 constraints 字段 ↔ constrained_by 边双向一致） | capability §1 第三条判据；B3 |
| 「某个码是什么含义」 | plugin/error_semantics.yaml（按日志消息文本命中有界语义类别）＋ plugin/error_codes.yaml 的 status 闸门 | Q27；见 references/trust-model.md §5 |

| 「这条知识该不该进本体」 | skill:bkn-updater（新增知识三问 ＋ 准入四关） | 另一 skill 的职责 |

## 4. 机制侧（diagnose_mechanism）**推不出**的四条

1. **因果链与根因定论**（N1；机制间边 0 实例 ⇒ chain_note 明说「因果层暂不可用」）。
2. **「受影响单元」的自动推导**——structural_evidence 只核了起点这半步；**给了 affected_unit** 才能把 checkable 从 partial 变 full（plugin/tools.py 的 _structural_evidence）。
3. **处置动作推导**——next_actions 是**取证**（look_for ＋ 该判据的 counter_check），不是处置；N6 仍是缺口。
4. **counter_check 的通用机检**——只有能写成「出现式」的否证条件才自动判；含**否定**语义（「dmesg 里无 OOM」）或**数值比大小**（「两处 GTID 相等」）的仍须人判。

---

## 5. 一句话纪律

**结构结论可以说「有路径、每跳带依据」；机制结论只能说「候选 ＋ 还差什么」。把后者说成前者，就是编造因果。**
