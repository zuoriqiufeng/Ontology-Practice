# 本体评审 rubric（三档严重度 ＋ 产物边界）

> **定位**：给「**先论证、后落**」（`24 号 §2.3` 准入四关）配一份**可执行的分档判据**——把「这份方案/改动能不能过」从**印象**变成**可复述的条目**。
> **与相邻件的分工**：`24 号 §2.3` 管**怎么加**（四关）；本件管**加之前怎么被挑毛病**；`doc/optimize/58-rules-and-invariants.md` 管规则落点；`scripts/gate.sh` 管**机器可判**的那部分。**三档只覆盖机器判不了的部分**——机器能判的一律走 lint / 门禁，不在这里重复。
> **来源**：OpenBKN 对照（对外部三档 `hard_stop` / `major` / `minor` 的**改写**，判据全部换成本仓语境）。依据见 `doc/comparison/openbkn-engineering/01-engineering-lifecycle.md` §3 与 `doc/optimize/70-ontology-optimization-plan.md` 批 O-3。

## 1. 什么时候用

| 场景 | 用不用 |
|---|---|
| 新增/修改本体元素（新命名空间 / 新轴 / 新类集 / 新关系类型 / 新公理） | **必用**（`24 号 §2.3` 四关的配套） |
| 新增关系类型 / 批量加边（≥5 条） | 必用 |
| 新增 Tool 或改 Tool 契约 | 必用 |
| 纯文档调整（doc/** 直改） | 不用（走 11 号变更自检清单） |
| 机器可判的项（段类型、引用完整性、裸码、清单一致性…） | **不用**——跑 `python3 plugin/scripts/lint_bkn.py` 与 `bash scripts/gate.sh` |

## 2. 三档判据

### 2.1 `hard_stop`（必须修订，不得带病落盘）

| # | 判据 | 为什么是 hard_stop |
|---|---|---|
| H1 | **与八条本体原则冲突**（`24 号 §2.4`），尤其是第二条「码不作知识」、第八条「只装机器拿不到且能纠正直觉的知识」 | 原则是判据基准，冲突即方向错 |
| H2 | **未过准入四关就动 `.bkn`**（无全范围论证文档 / 无评审记录） | 违反「先论证、后落」 |
| H3 | **样本不足却声称「收敛」**（第二关明文：样本太小不得称收敛） | 会造出「结构先行、内容为空」 |
| H4 | **该下延的值数据写进了本体**（算法、阈值、别名表、码表、公式…） | 违反值数据分工制（`24 号 §2.5`） |
| H5 | **无证据的断言**（把候选写成已确认、把推测写成结论、无来源的约束） | 违反来源侧车纪律（`plugin/provenance.yaml` 的存在理由） |
| H6 | **方案自称已生效 / 已通过**，而门禁尚未跑 | 误导下游 |

### 2.2 `major`（原则上修订；不修须在结论里说明理由）

| # | 判据 |
|---|---|
| M1 | **落点缺失或不具体**：说了要改但没写改哪个文件、哪个段 |
| M2 | **不可复现**：结论没有命令 / 没有数字 / 数字无出处 |
| M3 | **未与既有元素对位**（第三关要求「与既有元素全体对位：与谁重叠 / 与谁冲突 / 能否推导」） |
| M4 | **没有验收判据**：改完怎么知道成了 |
| M5 | **确认状态未分层**（已确认 / 候选 / 待业务确认 / 待裁定混在一起） |
| M6 | **影响面未评估**：会牵动哪些现行件、要不要同批更新（如 `24 号 §3` 与 capability 件的「必须同批」纪律） |

### 2.3 `minor`（可改可留，留则记录）

| # | 判据 |
|---|---|
| m1 | 表述不统一（编号、术语、表格字段名） |
| m2 | 章节顺序不利于评审 |
| m3 | 个别待确认问题未归类 |
| m4 | 结论摘要不够清晰 |

## 3. 产物边界（**评审独立成文**）

- findings **不写进被评审文档的正文**；落盘为独立文件（命名建议：`<件名>-verifier-findings.md`，随候选放 `attachments/` 或紧邻）。
- 每条 findings 必须含：**档位 / 判据编号（H·M·m） / 位置（文件:行或段） / 一句话问题 / 建议动作**。
- **Verifier 不改文档**（只出 findings）；修订由作者按 findings **定向**进行。

## 4. 修订循环与出口

- **顺序**：先修全部 `hard_stop`，再修 `major`；`minor` 可留（留则写进结论）。
- **轮次上限**：**自动修订最多 2 轮**；2 轮后仍有 `hard_stop` ⇒ 停止，输出未通过原因与所需材料。
- **不得**在修订中删除已确认事实（除确认状态本身有错）、**不得**把候选改写成已确认。

| 出口 | 条件 | 交付形态 |
|---|---|---|
| `pass` | 无 hard_stop，major 已处理或已解释 | 可进入候选流程（`doc/optimize/pending/`） |
| `warn` | 无 hard_stop，但仍有关键待确认 | 保持 `candidate` 标识 ＋ 待确认清单 |
| `fail` | hard_stop 未清除 | 不声明可评审；输出原因与补充材料清单 |

## 5. 与候选流程的衔接

```text
方案 → 本 rubric 出 findings → 修订（≤2 轮）→ 出口判定
  pass → 落 doc/optimize/pending/C-*/（candidate.json ＋ review.md ＋ payload/）
  warn → 同上，但 candidate.json 的 notes 必写待确认项
  fail → 不落候选，回补材料
```

> **最后一道**：`scripts/pending_apply.py` 由**人**触发并记名（`ledger.jsonl` 的 `by` / `reason` 非空）；**LLM 不得代批**（`doc/optimize/pending/README.md` 铁律 4）。
