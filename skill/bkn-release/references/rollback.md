# 回滚决策树（模块 2）

> **定位**：references/release-flow.md 回答"怎么发出去"；本文件回答"**发错了怎么退**"——
> 退到哪、怎么退、退完怎么留痕。
>
> **铁律**：**回滚 = 一次新发布**。不回写历史、不覆盖旧版本号、不"取消"已生效的事实——
> 版本号只前进（27 号 §0「发布不可覆盖」）。
>
> **原文来源**：原 doc/update/rollback.md（2026-10-15 清理）（153 行，27 号批 V-3）。命令、判据、顺序规则照原文；
> **引用一律纯文本路径**（AGENT.md R-1，不写链接）。**不触碰运行时**。
>
> **重试规则不在本文件**——三分类与重试上限**只在** references/release-flow.md §5b 定义（D5 单一事实源）。

## 0. 决策树

```text
出问题了
├─ 错处明确，且只涉及某几个文件的改动
│   ├─ 这些改动有候选来源（走过待审区）──▶ ① 定点恢复（§2）
│   └─ 无候选来源（手工编辑/更早期改动）──▶ ①b 从 git 或期初备份恢复（§3）
├─ 整批改动都不该上 ────────────────────▶ ② 批量恢复（§4）
└─ 错处不明 / 跨界 / 上面两条都不可用 ──▶ ③ 整版回退（§5）
```

**先回答两个问题再动手**：

1. **谁改的？** —— 找"**最后改写这些文件的候选**"（候选 `candidate.json.changes` 与 `payload/` 记录了它碰过什么）。
2. **`.pre-apply/` 还能用吗？** —— 备份只在**通过待审区 apply 落盘**时产生，位于
   `doc/optimize/pending/C-YYYYMMDD-NN/payload/.pre-apply/<相对路径>`（`scripts/pending_apply.py:170-181`）。

**最后改写者规则**：定点恢复会把文件退回"**那个候选落盘前**"的状态。若该文件此后又被**别的候选**改过，
这些后续改动会一并丢失——此时要么改走 §4/§5，要么只手工改回那一处并在 changelog 写明。
（`scripts/changeset.py --show <版本号>` 能列出某版本碰过哪些文件。）

**候选自带回滚预案**：28 号候选契约要求 `candidate.json` 有 `rollback` 字段——
本批演练时实测，缺该字段会被 `pending_status.py` 报结构性问题（见 §6）。**先看候选怎么写的，再动手。**

## 1. 分支① · 定点恢复（有候选来源）

```bash
cd <repo>/demo-product-bkn
C=doc/optimize/pending/C-YYYYMMDD-NN     # 产出这处改动的候选（= 最后改写该文件的候选）
F=bkn/objects/host.bkn                   # 出错的文件

diff "$C/payload/.pre-apply/$F" "$F"     # 看清"这次改动"到底是什么
cp -a "$C/payload/.pre-apply/$F" "$F"    # 恢复该文件到"该候选落盘前"
```

然后**按这个顺序**收尾（顺序不是形式，见下）：

```bash
python3 scripts/bkn_version.py --write --label "回滚 $C 的 $F（分支①）"   # ① 先升版
bash scripts/gate.sh --fast                                             # ② 再复验
python3 scripts/changeset.py --check --strict                           # ③ 再对账（写完 changelog 锚行）
# changelog 条目里写明：回滚了哪个候选的什么内容（+ 版本锚行）
```

> ⚠️ **顺序规则：「回滚 → 升版 → 复验」**。若先跑门禁，**③b（I14）一定红**——它判的是
> 「内容 ↔ 版本身份」一致性，内容刚回退、版本还指着旧内容，必然不一致。**那不是回滚失败**，
> 是顺序错了。`pending_apply` 内部也遵守同一条（先写版本再跑门禁，`pending_apply.py:195-198`）。

## 2. 分支①b · 无候选来源（手工编辑 / 更早期改动）

| 环境 | 手段 |
|---|---|
| 开发机（git 工作树） | `git checkout <提交> -- <文件>`；或 `git show <提交>:<文件> > <文件>`；已提交的一整段改动用 `git revert <提交>` |
| 现场（拷贝部署，非 git） | 从 `<repo>-backups/` 恢复——`manifest.json` 记录 `[{old, new, sha256, in_phase_baseline}]`，按 `sha256` 定位要恢复的旧文件 |

收尾与分支①相同（升版 → 复验 → 记录）。

## 3. 分支② · 批量恢复（整批改动都不该上）

把该候选 payload 覆盖过的每个文件全部还原（= 把它的 `.pre-apply/` 逐个拷回）：

```bash
C=doc/optimize/pending/C-YYYYMMDD-NN
cd "$C/payload/.pre-apply"
find . -type f | while read -r f; do cp -a "$f" "<repo>/${f#./}"; done
```

两条补充规则：

- **候选"新增"的文件**（`.pre-apply/` 里没有对应项）在回滚时应当**删除**——它们是被加进生效树的。
  删之前逐个确认它确实是该候选新增的（对照 `candidate.json.changes`）。
- **已 `applied` 的候选不"取消"**：它的账本 `approve` 与 `status` 都是事实，不改回。
  回滚的表达是**新版本 + changelog 条目**（写明"回滚 C-… 的哪些内容"），
  并在该候选 `review.md` **追加**一行回滚记录（只追加，不改原审批记录）。

## 4. 分支③ · 整版回退

| 现场形态 | 手段 | 注意 |
|---|---|---|
| 开发机（git 工作树） | `git revert <提交>`（已提交）/ `git checkout HEAD -- bkn/`（未提交）；需要标记时 `git tag <版本号>`——**tag 名 = 版本号本体**，不新造第三套编号 | 仓库**无 remote**；tag 只在本地，别当成异地备份 |
| 拷贝部署（非 git） | 用期初备份目录 `<repo>-backups/`（`manifest.json` + 68 文件批次清单） | 它是**"期初"快照**（改动前状态），**不是每版快照**——只能退回改变之前的基线。要退到"某个中间版本"需要该版本自身的副本（27 号 §2.1 刻意不做版本目录堆叠；按需用 `git worktree`/临时目录拉起，见 27 号 Q19） |

回退后同样：**升版 → 复验 → 记录**（`--write --label "整版回退到 <内容描述>"`）。

## 5. 门禁红且不是 I14 怎么办

回滚后复验若在**别的门**红（lint / 结构量 / 基线），说明**回滚目标本身与现行规则冲突**——
典型：回滚一次"清理/收敛"候选，会把已退场的元信息或退场概念带回来，触发零冗余机检或退场词检查。

此时**不要盲目照抄**，二选一并在 changelog 写明理由：

- **定点修正**：不走整文件恢复，只把真正错的那一处改回去（保留该候选的其余成果）；
- **回滚 + 适配**：回滚的同时准备一个新候选，把"被带回来的旧内容"按现行规则重做一遍。

## 6. 演练记录（2026-10-10，隔离副本）

**可复现来源**：`python3 scripts/drill_rollback.py`（默认副本 `/tmp/v3drill`，不触碰生效内容）。
它完整走：建副本 → 造一个"改错了"的候选（只加一个尾随空行，零语义影响）→ 走待审区落盘
→ 按分支①恢复 → 升版 → 复验。

关键输出（原文摘录）：

```text
改动前 bkn/objects/host.bkn sha256 = b3554d77a2251ceb…
$ python3 scripts/pending_apply.py C-20261010-90
版本身份（27 号 V-0）：✅ 已写 bkn-version.json：bkn-20261010-2（38 文件，hash 43d4e32939d4d9f5…）
改动后 sha256 = 59dc7148be36d262…（与改动前不同：True）
候选 .pre-apply 备份存在：True

## 4a. 先跑门禁 → ③b 红（预期：顺序规则）
  ❌ ③b 本体已改但版本未升级——跑 scripts/bkn_version.py --write

## 4b. 升版 → ✅ 已写 bkn-version.json：bkn-20261010-3（38 文件，hash 882215ead630056b…）

## 4c. 复验 → ✅ 全部门禁通过（① lint=0 ② pytest 443 passed ③a 结构量持平 ③b I14 一致）

结论: ✅ 演练通过（分支① 可用）
```

三个结论：

1. **内容精确回到改动前**（`sha256` 一致）——`.pre-apply/` 足以支撑定点恢复；
2. **版本号前进而非回写**：`bkn-20261010-2`（坏内容）→ `bkn-20261010-3`（恢复后），
   而 `-3` 的 `version_hash` **等于**最初 `-1` 的 hash——同一份内容重新发布，身份是新的；
3. **顺序规则被实证**：先跑门禁必红 ③b（不是失败）；且演练暴露了候选契约的一个字段要求——
   `candidate.json` 缺 `rollback` 会被 `pending_status.py` 报结构性问题。

## 7. 一页速查

```text
错一处 + 有候选     → cp -a 候选/payload/.pre-apply/<文件> <文件>；升版 → 复验 → 记录
错一处 + 无候选     → git checkout <提交> -- <文件>（现场用期初备份）；升版 → 复验 → 记录
错一批              → 逐个拷回 .pre-apply；该候选新增的文件要删；候选状态不改
整版不可用          → git revert / 期初备份目录；升版 → 复验 → 记录
门禁红且不是 I14    → 回滚目标与现行规则冲突 → 定点修正 或 回滚+适配（写进 changelog）
任何时候            → 回滚 = 一次新发布；版本号只前进；changelog 必写
```
